# 可行性评估与一周执行计划(Phase 1~4)

> 本文档回答一个问题:**「能开源就开源,加上 AI 辅助,一周内能否在开发板上跑通?」**
> 结论基于 2026-08-17 对代码库现状的审查,以及已确认的三个前提条件。
> 权威技术细节以 `IMPLEMENTATION_PLAN.md` 为准,本文档是它的**执行视角补充**。

---

## 0. 结论摘要(Executive Summary)

| 问题 | 结论 |
|---|---|
| 全 6 个 Phase(含语言嵌入 3DGS + 文本查询)一周跑通? | **不现实**,正常节奏 4~8 周 |
| **Phase 1~4**(数据流 + RGB-D 3DGS-SLAM 基线 + 基础优化 + ROS2 接口)一周跑通? | **现实可行**,但有 1 个关键风险点 |
| 项目 90% 组件是否开源? | 是,SplaTAM / diff-gaussian-rasterization / librealsense / ROS2 / MobileSAM / MobileCLIP 全部开源 |
| 项目代码现状 | **文档 + 骨架**,算法代码为 0 行,从零开始 |

一句话:**一周可以跑通一个有意义的 SLAM 基线,但跑不通整个语言嵌入系统,且成败取决于一个 CUDA 扩展能否在板子上编译。**

## 2. 目标范围与前提(已确认)

| 项 | 确认值 |
|---|---|
| **目标范围** | **Phase 1~4**(非全 6 Phase) |

| **相机** | Intel RealSense D435i(已到手) |
| **开发方式** | **全程在板子上开发**(本机即目标机,无跨架构搬运) |

**Phase 1~4 的定义**:
- **Phase 1**:D435i 数据流打通(Docker → librealsense → 对齐 RGB-D + IMU + 内参)
- **Phase 2**:RGB-D 3DGS-SLAM 基线(Tracking + Mapping,免 COLMAP)
- **Phase 3**:基础优化(关键帧管理 / 高斯剪枝 / 视锥剔除)— 一周内做**基础版**
- **Phase 4**:ROS2 具身接口(订阅 RGB-D,发布 `/tf` + 高斯点云)

**明确排除在一周范围外**:Phase 5(MobileSAM+MobileCLIP 特征工厂)与 Phase 6(语言嵌入 3DGS + 文本查询),留作后续阶段。

## 3. 可行性判断:为什么一周"可行"也"有风险"

### 3.1 有利因素(把一周从不可能变可能)

1. **板子与相机已就绪**——排除了最大的时间黑洞(环境搭建/硬件调试)。
2. **全程板端开发**——编译、运行、调试同机,无跨架构往返。
3. **90% 组件开源且成熟**——librealsense、ROS2、graphdeco rasterizer 都是活跃维护的成熟项目,我们做的是**移植 + 集成 + 优化**,不是发明。
4. **`IMPLEMENTATION_PLAN.md` 提供了全部核心公式与接口契约**——Tracking/Mapping 的损失函数、参数化、关键帧逻辑都写清楚了,可在 AI 辅助下直接翻译成代码。
5. **AI 辅助**——大量机械性、模板性代码(数据结构、IO、脚本、ROS2 节点骨架)可以大幅提速。

### 3.2 关键风险点(整个计划就这一个"成败开关")

> **SplaTAM 的 diff-gaussian-rasterization CUDA 扩展能否在 aarch64 / sm_87 上编译通过。**

- 计划附录 B 将它标为**高风险**,这是全项目最大的不确定项。
- 影响:编译通过 → 后续很顺,一周达成 Phase 1~4;编译受阻 → 必须先降级(纯 PyTorch 慢速 splat 保正确性),"实时"目标延后。
- 对策见下一节"策略调整"。

### 3.3 一周的期望管理

- **"跑通" ≠ "实时"**。计划中的 **15–30 FPS 是 Phase 3 的长期优化目标,不是一周内能保证的**。SplaTAM 在桌面 GPU 上约 ~10 FPS,Orin NX 上一周内能做到"跑起来、结果正确",实时性留到后续优化。
- 一周的合理成果:**D435i 输入 → SLAM 跑通 → 输出轨迹 + 高斯地图 → ROS2 发布**。这已是可演示、可写简历的里程碑。

## 4. 关键策略调整:不要原样跑 SplaTAM 仓库

计划原稿思路是"SplaTAM 蓝本,clone 下来改"。**建议调整**,理由:

- SplaTAM 是研究仓库(非 pip 包),即使在桌面 x86 也以难跑著称:锁旧 torch 1.12、带 GUI 依赖、rasterizer 是 2023 年的老 fork。
- 在 aarch64 + torch 2.x(Jetson PyTorch for Jetson)下,预期需要打多处补丁,**一周的紧排期经不起这个不可控**。

### 4.1 三条腿并行铺开

**① 主力腿(最稳)——官方 rasterizer + 自写 SLAM 循环**

| 组件 | 来源 | 说明 |
|---|---|---|
| `diff-gaussian-rasterization` | `graphdeco-inria` 官方仓库(活跃维护) | torch 2.x 兼容;编译只须 `TORCH_CUDA_ARCH_LIST="8.7"` |
| depth 渲染通道 | 参考 SplaTAM 的扩展实现自行补充 | 官方 rasterizer 不渲染 depth,需加一个输出通道(有现成实现可抄) |
| Tracking / Mapping 循环 | **按 `IMPLEMENTATION_PLAN.md` 2.4 节公式自写** | 约 500~800 行;公式、损失、关键帧逻辑文档已齐 |

**② 降级腿——纯 PyTorch 慢速 splat**

- 若 CUDA 扩展编译受阻,先用**纯 PyTorch 自动求导**实现慢速 splat(显式深度排序 + α 混合)。
- 目的:**先验证数学正确性**,再并行攻 CUDA 编译。
- 这是计划 2.5.3 已写明的退路。

**③ 并行腿——Phase 5 铺路(可选,空闲时做)**

- MobileSAM + MobileCLIP 与 SLAM **互不依赖**(计划 0.4),可并行验证单帧掩码 + 特征。
- 只作 week 2 语言嵌入的铺垫,**不占 Phase 1~4 的排期**。

> **决策点**:开工 D1 先快速试 SplaTAM fork rasterizer 的编译(它有现成 depth 通道);若 1 天内反复受阻,立即切到主力腿(官方 rasterizer + 自写)。不恋战。

## 5. 一周排期(板端,Phase 1~4)

| 天 | 内容 | 产出 / 验收 |
|---|---|---|
| **D1** | 环境盘点 + Docker 构建 | 容器内 `torch.cuda.get_device_capability() == (8,7)`;NGC 镜像 tag 核对无误 |
| **D2** | librealsense 编译(RSUSB 后端)+ D435i 数据流 + 深度反投影验证 | Phase 1 验收通过:RGB-D 对齐、`K` 合理、反投影出 `.ply` 无错位 |
| **D3–D5** | **主力攻坚**:rasterizer 编译 + depth 通道 + Tracking/Mapping 写通 + Replica 数据集验证 | Phase 2 验收:ATE 达 cm 级,输出渲染图 + `.ply`,数值/解析梯度互验 |
| **D6** | D435i 自采序列跑通 + 基础优化(关键帧 / 剪枝 / 视锥剔除) | 长序列稳定不崩,无 OOM,给出基础 FPS 数据 |
| **D7** | ROS2 节点封装 + 收尾 | Phase 4 最小可用:`/tf` + 高斯点云发布;`colcon build` 通过;留 1 天 buffer |

**关键路径**:D3–D5 的 rasterizer 编译 + SLAM 循环实现,是全周的关键路径,需在 D3 就立即启动。

## 8. 环境盘点清单(开工 D1 第一件事)

以下四项必须逐项确认,是 Phase 1 的入场券:

1. **架构确认**
   - `uname -m` 应为 `aarch64`
   - `nvidia-smi` 能识别 Ampere GPU(Orin NX,1024 CUDA 核)
2. **JetPack 版本**
   - `cat /etc/nv_tegra_release` 或 `nvcc --version`,确认 **JetPack 6.2 / L4T 36.4 / CUDA 12.x**
3. **网络**
   - 能否访问 `catalog.ngc.nvidia.com`(拉镜像)与 `pypi.ngc.nvidia.com`(torch wheel)
   - 国内环境通常需代理,提前配置
4. **磁盘空间**
   - 预留 **30~40GB**:docker 镜像 + torch wheel + librealsense 源码编译 + Replica 数据集
